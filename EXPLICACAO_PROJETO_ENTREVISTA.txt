GUIA COMPLETO DO PROJETO PARA ENTREVISTAS: CONTROLE DE FLUXO VIARIO
================================================================================

1. PITCH DO PROJETO (COMO EXPLICAR EM 30 SEGUNDOS)
--------------------------------------------------------------------------------
"Desenvolvi uma solucao serverless e 100% automatizada em Python para auditoria e
monitoramento periodico de fluxos em radares de transito. A aplicacao roda duas
vezes ao dia de forma automatica na nuvem via GitHub Actions, acessa o portal
restrito com Playwright, analisa dinamicamente cada radar e faixa, identifica
anomalias (como faixas vazias, sem geracao de fluxo ou com alertas em vermelho) e
alimenta em tempo real uma planilha compartilhada no Google Sheets, separando o
historico geral das pendencias tecnicas urgentes. Tudo isso a custo zero de
infraestrutura e com seguranca avancada de credenciais."


2. QUAL PROBLEMA DE NEGOCIO O PROJETO RESOLVE?
--------------------------------------------------------------------------------
* O Problema: Antes, os tecnicos ou operadores precisavam acessar manualmente o
  portal da empresa, aplicar filtros equipamento por equipamento, checar faixas e
  anotar problemas. Isso consumia tempo, gerava risco de erro humano e atrasava a
  manutencao de radares apagados/com defeito.
* A Solucao: Um robo confiavel que roda pontualmente (as 07:50 e 13:30), varre
  todos os radares, detecta qualquer falha visual ou numerica e entrega uma lista
  pronta de acoes para a equipe tecnica antes do inicio do expediente.


3. STACK DE TECNOLOGIAS E JUSTIFICATIVA TECNICA DAS ESCOLHAS
--------------------------------------------------------------------------------
* Python 3.11: Linguagem robusta, limpa e padrao da industria para automacao,
  analise de dados e web scraping.
* Playwright (Headless Browser): Escolhido em vez do antigo Selenium por ser muito
  mais moderno, rapido, possuir esperas inteligentes e automaticas (auto-waiting)
  de elementos do DOM e renderizar estilos CSS (cores vermelhas/alertas) com precisao.
* Google Sheets API + gspread + google-auth: Utilizado para entregar os dados em
  uma interface em nuvem familiar aos funcionarios, sem necessidade de instalar
  softwares ou criar paineis complexos. Usa Conta de Servico (Service Account).
* GitHub Actions (CI/CD & Cron Serverless): Orquestrador em nuvem gratuito que
  executa o script nos horarios agendados (UTC 10:50 e 16:30 -> Brasilia 07:50 e 13:30)
  sem precisar manter um servidor ou maquina local ligada.
* Dataclasses & Pydantic Concepts: Estruturacao orientada a objetos com tipagem
  forte (models.py), garantindo integridade dos dados e facilidade de manutencao.
* Python unittest: Suite de testes unitarios garantindo que a logica de deteccao de
  erros e configuracao funcione mesmo sem conexao externa.


4. COMO O SISTEMA FUNCIONA POR DENTRO (FLUXO PONTA A PONTA)
--------------------------------------------------------------------------------
Passo 1: O GitHub Actions e disparado pelo cron agendado (ou por clique manual).
Passo 2: O sistema carrega as variaveis e credenciais seguras do GitHub Secrets.
Passo 3: O Playwright abre o navegador em segundo plano e realiza o login no portal.
Passo 4: O scraper le o filtro de selecao de equipamentos (<select>) e obtem a
         lista de radares cadastrados.
Passo 5: Para cada equipamento, o robo aplica o filtro, aguarda o carregamento
         dos dados (espera reativa) e extrai os dados das faixas (valores e cores).
Passo 6: O modulo 'FlowAnalyzer' processa as leituras:
         - Se tiver classe de cor vermelha (ex: 'bg-danger', 'alert', 'red') -> FALHA.
         - Se o valor estiver vazio, 'N/A' ou ausente -> FALHA.
         - Se estiver com valor normal -> OK.
Passo 7: O servico 'SheetsService' autentica no Google via Service Account e grava
         em lote (batch append) em duas abas:
         - 'Historico_Geral': Todas as leituras para auditoria cronologica.
         - 'Pendencias_Tecnicas': Apenas os radares com falha para o tecnico agir.


5. DESAFIOS DE ENGENHARIA SUPERADOS (EXCELENTE PARA CONTAR EM ENTREVISTAS)
--------------------------------------------------------------------------------
1. Filtro com 1 Equipamento por Pagina:
   - Desafio: O portal nao listava todos os dados de uma vez, exigia mudar o filtro.
   - Solucao: Implementacao de um loop com tratamento de timeout isolado por
     equipamento, garantindo que a lentidao de um radar nao trave a auditoria dos outros.

2. Deteccao Precisa de Status Visual (Cor Vermelha):
   - Desafio: Alguns portais indicam falha pela cor da celula e nao por texto explicito.
   - Solucao: O FlowAnalyzer inspeciona atributos CSS (classes e estilos inline hex/rgb)
     alem de validar se o valor numerico esta vazio ou zerado.

3. Otimizacao de Requisicoes no Google Sheets (Rate Limits):
   - Desafio: A API do Google tem limite de gravacao por minuto.
   - Solucao: Gravacao em lote (append_rows) consolidada ao final do escaneamento,
     fazendo pouquissimas chamadas de rede em vez de gravar linha por linha.

4. Seguranca e Zero Credenciais no Codigo (DevOps / SecOps):
   - Nenhuma senha, token ou JSON de chave privada fica salvo no codigo. Tudo e
     injetado como variavel de ambiente e GitHub Secrets protegidos.


6. PERGUNTAS TIPICAS DE ENTREVISTA E COMO RESPONDER
--------------------------------------------------------------------------------
P: "Por que voce escolheu Playwright em vez de requests/BeautifulSoup puro?"
R: "O site possui autenticacao dinamica, seletores de filtro por equipamento e
indicadores visuais de cor (status vermelho) renderizados via JavaScript. O
Playwright renderiza o DOM exatamente como um usuario real e possui auto-waiting,
o que evita falhas comuns de sincronismo em conexoes lentas."

P: "Por que usar Google Sheets em vez de um banco de dados SQL (ex: PostgreSQL)?"
R: "Foco no usuario final (regra YAGNI). A equipe tecnica e operacional ja utiliza
planilhas no dia a dia no celular e no computador. O Google Sheets serviu como um
painel compartilhado em tempo real sem custo de hospedagem e sem necessidade de
criar e manter um frontend proprio."

P: "Como voce garantiu a seguranca dos acessos e senhas?"
R: "Utilizei o principio de minimo privilegio com Service Accounts do Google Cloud
e centralizacao de segredos no GitHub Secrets. No ambiente local, usei arquivos .env
que sao estritamente ignorados pelo .gitignore, impedindo qualquer vazamento no Git."

P: "O que acontece se a conexao oscilar ou o portal estiver fora do ar?"
R: "O sistema possui tratamento robusto de excecoes. Se o login falhar ou a pagina
der timeout, ele gera um log detalhado, finaliza a sessao do navegador de forma limpa
para nao consumir memoria e avisa o status no log de execucao do GitHub Actions."


7. RESUMO DAS METRICAS DE IMPACTO
--------------------------------------------------------------------------------
* Custo de Infraestrutura: R$ 0,00 (100% gratuito utilizando GitHub Actions e Google APIs).
* Tempo de Execucao: ~1 a 2 minutos por ciclo completo de auditoria.
* Economia de Tempo: Eliminacao total da necessidade de checagem manual diaria.
* Confiabilidade: Execucoes pontuais garantidas 365 dias por ano.
